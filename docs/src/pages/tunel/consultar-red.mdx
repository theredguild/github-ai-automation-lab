# Consultar health desde la red interna

Si health ya devuelve 200 desde el host y Next sigue activo, vamos a consultar desde otro container. Ejecutá este comando en la terminal de consultas del host, en la raíz de `lab`, no en la shell ocupada por Next. Docker creará un cliente temporal para hacer la prueba:

```bash
docker run --rm --network red-taller \
  taller \
  curl -i http://lab-app:3000/api/health
```

Buscá HTTP 200 y compará el JSON con el que recibiste desde el host:

```text
{"status":"ok","service":"nodoserrano"}
```

Esta vez Docker resuelve `lab-app` a su dirección interna dentro de `red-taller`. No es un dominio público ni un nombre que deba resolver el host. El cliente llega directamente al puerto 3000 del container, sin pasar por el puerto publicado del host, y desaparece al terminar gracias a `--rm`. La respuesta debe ser la misma porque seguimos consultando el mismo origen, aunque cambie el camino.

| Desde dónde preguntás | Dirección del origen |
| --- | --- |
| Host | `http://127.0.0.1:3000` |
| Dentro de lab-app | `http://127.0.0.1:3000` |
| Otro container en red-taller | `http://lab-app:3000` |
| Cliente externo, después del túnel | URL HTTPS impresa por cloudflared |

**No sigas si** falla esta consulta interna aunque funcione desde el host. Revisá nombre, red compartida y escucha `0.0.0.0`; un túnel no arregla un origen inaccesible.
