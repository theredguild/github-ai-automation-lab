# Solicitar review del SHA corregido

**Dónde:** navegador, **Labels** del PR propio y Recent Deliveries del hook nativo; host en `lab` para consultar estado. **Antes:** [corrección publicada](/review/publicar-correccion), SHA nuevo anotado y PR Open, no draft, `development → main` del mismo repo.

Después del push, quitá **ai-review** y volvé a agregarla desde el selector web. Si estaba ausente, agregala. Debe ocurrir una transición nueva a presente que produzca `labeled`. **No repitas una entrega antigua** para pedir review de commits nuevos.

Seguí la nueva entrega:

1. GUID nuevo, etiqueta `ai-review` y PR correcto en Recent Deliveries.
2. SHA head recibido igual al commit corregido. Anotá también el base recibido.
3. Filtros coincidentes y tarea aceptada en el gateway. 202 aún no significa comentario.
4. Comentario nuevo en el PR, con **ambos SHA** revisados. Su head debe ser el SHA corregido, no el de la suma.

En el host podés contrastar el estado actual:

```bash
git rev-parse HEAD
gh pr view NUMERO --json baseRefName,baseRefOid,headRefOid
gh pr view NUMERO --web
```

Leé la respuesta nueva con [los mismos criterios críticos](/review/leer-review). Debe analizar la versión corregida, no arrastrar como hallazgo actual una suma que ya no está. Un aviso de solicitud desactualizada no es una revisión: significa que cambió base o head y habrá que solicitar otra vez sobre el estado actual.

**Comprobación:** GUID nuevo y comentario nuevo corresponden a base/head solicitados; head es el SHA corregido. Los controles por instrucciones siguen sin hacer atómica la publicación.

**No sigas si** el comentario corresponde al SHA viejo, sólo tenés 202 o el estado cambió durante el trabajo. Reconciliá la evidencia y pedí un evento fresco cuando el PR esté estable. No avances a merge por ausencia de críticas del modelo.
