# Reiniciar Next con la configuración nueva

Con la [configuración privada completa](/webhook/preparar-receptor) y ningún secret versionado, vamos a reiniciar Next para que lea las variables nuevas. Volvé a la terminal de `lab-app` donde corre el servidor, en `/workspace`, el proyecto montado desde `lab`. El túnel puede seguir abierto.

Detené **sólo el proceso Next de esta práctica** con **Ctrl+C** en su propia terminal. No arranques un segundo servidor sobre el mismo puerto.

Si cambiaste código del receptor y no sólo `.env.local`, primero reconstruí en esa shell:

```bash
pnpm build
```

Con el build disponible, iniciá el proceso que leerá la configuración:

```bash
pnpm start --hostname 0.0.0.0
```

Dejá ese proceso activo y, desde otra terminal del **host** en la carpeta `lab`, comprobá que la app responda:

```bash
curl -i http://127.0.0.1:3000/api/health
```

Next debe escuchar sin conflicto de puerto y health debe responder 200 con el servicio esperado. Con esto comprobamos disponibilidad, todavía no la firma ni la aceptación de eventos. Recordá que el `0.0.0.0` del proceso es interno al container. El puerto publicado del host sigue limitado a loopback.

**No sigas si** falló el build, hay dos procesos compitiendo por 3000 o health no corresponde a tu app. Hermes no reinicia este container; no le montes el socket Docker para hacerlo. La prueba de 401 requiere este reinicio previo.
