# Leer workflow, job y steps

**Dónde:** host, editor en `lab`, rama `development`. **Antes:** imagen explorada y repositorio propio publicado.

Abrí `docs/snippets/checks.yml`. Viajó con la app y ya no está en `hackerspace-site/` dentro del checkout del material. Leé el archivo completo. Todavía no está activado en `.github/workflows/`.

GitHub Actions organiza el trabajo así:

| Parte | Qué significa acá |
| --- | --- |
| Workflow | Archivo YAML que define cuándo ejecutar trabajo y qué jobs contiene |
| Ejecución o run | Una vez que se inicia ese workflow, con un ID y un commit concretos |
| Job | Conjunto de pasos que se ejecuta en un runner; acá se llama `check` |
| Step | Un paso del job, como descargar el código o ejecutar `pnpm typecheck` |
| Runner | Programa que recibe el job y ejecuta sus steps en su entorno |
| Check | Resultado que GitHub muestra para ese trabajo sobre un commit |

CI significa integración continua: ejecutar comprobaciones repetibles sobre cambios de código para detectar fallas antes de integrarlos. Acá practicamos esas comprobaciones con inicio manual. Publicar un commit, iniciar el workflow y obtener un resultado son acciones distintas.

Diagrama del taller; ejemplo conceptual.

La primera parte dice:

```yaml
name: Checks del workshop
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  check:
    runs-on: [self-hosted, linux, workshop]
    timeout-minutes: 10
```

`workflow_dispatch` permite el inicio manual. No hay un trigger `push`: enviar un commit no ejecutará este workflow. `workshop` debe coincidir con la etiqueta del runner. `contents: read` limita la credencial del job y el timeout limita su duración.

Dentro del mismo job:

```yaml
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
        with:
          persist-credentials: false
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
```

Checkout descarga en el runner el código de la versión que se va a comprobar. Está fijado a un commit de la acción y no conserva su credencial en Git. La instalación respeta el lockfile; Biome revisa reglas de código y TypeScript comprueba tipos sin necesitar abrir la página en un navegador.

Los steps corren en orden. Si uno falla, los siguientes de este archivo no se ejecutan y el job queda fallido. Un check verde sólo confirma las comprobaciones incluidas aquí: este workflow no ejecuta tests ni hace un deployment.

Comprobá en el archivo real el evento, las etiquetas y los cuatro steps. **No sigas si** el contenido no coincide o apunta a otro runner.
