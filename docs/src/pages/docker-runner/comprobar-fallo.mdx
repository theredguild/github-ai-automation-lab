# Ejecutar y comprobar la falla

**Dónde:** navegador o terminal del host en `lab`, rama `development`. **Antes:** segundo runner escuchando y SHA del error publicado.

**Elegí un solo dispatch.** En web, **Actions → Checks del workshop → Run workflow → development → Run workflow**. Alternativamente, desde el host con Actions: Read and write:

```bash
gh workflow run checks.yml --ref development
gh run list --workflow checks.yml --limit 5
```

Anotá el nuevo `RUN_ID`. Comprobá en el navegador que corresponde a `development` y al SHA del error, no al baseline. Consultá un estado puntual y abrí los steps:

```bash
gh run view RUN_ID --json status,conclusion
gh run view RUN_ID --web
```

Si está en cola, comprobá escucha y etiquetas `self-hosted`, `linux`, `workshop` antes de cambiar código. Cuando termine, buscá el step `pnpm typecheck`, el archivo y la línea. También podés leer los logs fallidos desde el host:

```bash
gh run view RUN_ID --log-failed
```

Mensaje esperado, presentado como ejemplo:

```text
app/estado.ts(1,14): error TS2322:
Type 'string' is not assignable to type 'number'.
```

La evidencia requerida es `completed` con `failure`, en el SHA del error, y una falla de tipos por asignar string a number. Un fallo de descarga o de runner no demuestra esta prueba. El segundo runner debe salir después de su único job.

No uses `gh run watch`. **No sigas si** el run está en otro SHA o falló por otra causa: leé el primer step fallido antes de corregir la prueba.
